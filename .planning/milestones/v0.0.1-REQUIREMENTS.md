# Requirements: data-hub

**Defined:** 2025-03-18
**Core Value:** Data from connected integrations flows reliably into the platform with strict validation — if it's in the database, it's valid.

## v1 Requirements

Requirements for initial release. Each maps to roadmap phases.

### Kernel

- [x] **KERN-01**: AddData command accepts table name, source ID, schema hint, and raw data
- [x] **KERN-02**: Strict schema validation rejects malformed data before persistence
- [x] **KERN-03**: DataAdded event emitted on successful data addition
- [x] **KERN-04**: Commands, queries, and events have zero external dependencies (pure Python)
- [x] **KERN-05**: Ports define interfaces for repository and event publisher

### Persistence

- [x] **PERS-01**: Data persisted to SQLite (v1) / PostgreSQL (v2) with ACID guarantees
- [x] **PERS-02**: Repository adapter implements kernel port interface
- [x] **PERS-03**: Audit trail captures: timestamp, source_id, table_name, status
- [x] **PERS-04**: Idempotent processing prevents duplicate records from retry storms

### Transport

- [x] **TRAN-01**: FastAPI endpoint receives Nango webhooks
- [x] **TRAN-02**: Webhook acknowledged within 5 seconds (fast ack pattern)
- [x] **TRAN-03**: Webhook signature verified on raw bytes before processing
- [x] **TRAN-04**: Health check endpoint returns service and database status

### Observability

- [x] **OBSV-01**: Structured logging with correlation IDs for request tracing
- [x] **OBSV-02**: Validation failures logged with full context (source, schema, data sample)
- [x] **OBSV-03**: Data quality metrics tracked: validation failure rate, processing latency

### Verification

- [x] **VERF-01**: Verification capability confirms data was stored correctly

## v2 Requirements

Deferred to future release. Tracked but not in current roadmap.

### Resilience

- **RESL-01**: Automatic retry with exponential backoff for transient failures
- **RESL-02**: Dead letter queue stores failed records for inspection and replay

### Schema Management

- **SCHM-01**: Schema drift detection alerts when incoming data shape changes unexpectedly
- **SCHM-02**: Schema versioning tracks evolution over time

### Query

- **QURY-01**: Generic QueryData command supports flexible query formats
- **QURY-02**: Query results paginated for large datasets

### Extended Observability

- **EOBS-01**: Column-level lineage tracks source field to destination mapping
- **EOBS-02**: Dashboard visualizes data quality metrics over time

## Out of Scope

Explicitly excluded. Documented to prevent scope creep.

| Feature | Reason |
|---------|--------|
| Real-time streaming | Webhooks are micro-batch; <5s latency is sufficient |
| Transformation during ingestion | ELT pattern — transform downstream, not at ingestion |
| General HTTP API | Nango webhooks only for v1; keeps transport layer focused |
| Multiple storage backends | SQLite for v1, PostgreSQL for production — hexagonal architecture enables easy swap |
| Low-code UI | Code-first configuration in Git; focus on kernel quality |
| Custom transformation per integration | Becomes unmaintainable at scale; store raw, transform downstream |
